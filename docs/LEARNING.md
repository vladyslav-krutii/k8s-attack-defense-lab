## Phase 0 — кластер kind + Calico (`2854801`)

**Що.** Локальний кластер kind `k8s-lab` (control-plane + worker, K8s 1.36.4,
образ вузла закріплений за digest). Стандартний CNI вимкнено
(`disableDefaultCNI`), замість нього Calico v3.33 через Tigera operator.
`make verify-netpol` перевіряє, що NetworkPolicy справді застосовуються.

**Навіщо.** Вбудований CNI kind (kindnet) **ігнорує** NetworkPolicy: політика
створюється, але нічого не блокує. Без Calico сценарій 3 і шар захисту 3 були
б «зеленими на папері». Digest замість тегу: тег можна перезаписати, digest
ні, тож кластер відтворюється байт-у-байт.

**Питання на співбесіді.**
- Чому NetworkPolicy може «не працювати», хоча `kubectl apply` пройшов?
- Чим відрізняється закріплення за тегом і за digest?
- Як ти перевіриш, що CNI справді enforce-ить політики?

## Phase 1 — демо-застосунок і base-маніфести (`2854801`)

**Що.** Три сервіси: `web` (nginx-unprivileged) → `api` (Node/TypeScript) →
`db` (Postgres). Kustomize base без навмисних помилок і без захисту.
`make smoke` створює і читає нотатку через увесь ланцюжок.

**Навіщо.** Потрібен реалістичний, але маленький ланцюжок, щоб атаки мали
що ламати (секрет БД, мережевий шлях до БД). Smoke-тест гарантує, що
захист не зламав сам застосунок: безпека, яка ламає продукт, буде вимкнена.

**Питання.**
- Чим readiness відрізняється від liveness, і чому `/readyz` перевіряє БД,
  а `/healthz` ні?
- Навіщо multi-stage Dockerfile і `USER 1000:1000`?

## Phase 2 — vulnerable overlay і сценарії 1–3 (`099d442` … `faa39f3`)

**Що.** Overlay `vulnerable` з трьома помилками конфігурації та сценарії з
`run.sh` (демонстрація впливу) і `verify.sh` (exit 0 EXPLOITABLE / 1 BLOCKED /
2 INCONCLUSIVE):
1. privileged pod + `hostPath: /` → читання файлів вузла, kubelet PKI;
2. RoleBinding на `edit` + автомонтований токен SA → читання Secret через API;
3. немає NetworkPolicy → `web` дістається до `db:5432`.

**Навіщо.** Кожен сценарій показує *вплив* мінімально (ім'я секрету, marker
файл), без деструктиву. Окремий код INCONCLUSIVE потрібен, щоб зламаний тест
не виглядав як «захищено» (control check перед атакою).

**Питання.**
- Чому privileged + hostPath фактично дорівнює root на вузлі?
- Що може зробити под з токеном SA, прив'язаним до `edit`?
- Як уникнути хибного «BLOCKED» в автоматичній перевірці?

## Phase 3 — hardened overlay, три шари (`5405ae0` … `032ccf1`)

**Що.** Захист шарами, після кожного видно, який `verify.sh` перемикається:
1. Pod Security Admission `restricted` (enforce закріплений на v1.36) +
   securityContext (non-root, drop ALL, seccomp RuntimeDefault);
2. окремий ServiceAccount на кожен workload, без RBAC,
   `automountServiceAccountToken: false`;
3. default-deny NetworkPolicy + явні дозволи (web→api, api→db, DNS).

Потім overlay перебазовано на base (рендер байт-у-байт той самий).

**Навіщо.** Пошарова побудова доводить, *який саме* контроль закриває
*яку саме* атаку. Закріплена версія PSA (`enforce-version`) не дає оновленню
кластера раптово зламати деплой; `warn/audit=latest` попереджає заздалегідь.

**Питання.**
- Чому в NetworkPolicy `namespaceSelector` і `podSelector` в одному елементі
  `to:` означають AND, а в двох елементах — OR?
- Навіщо закріплювати `enforce-version`, а warn/audit лишати `latest`?
- Чому не можна просто прибрати RBAC, а треба ще й вимкнути автомонтування
  токена?

## Phase 4, крок 1 — закріплені інструменти (`b26e517`, `885428f`)

**Що.** Скрипти встановлення Helm v4.3.2, kubectl v1.36.4, Kyverno CLI v1.20.0
у `~/.local/bin` з перевіркою SHA-256, ідемпотентні.

**Навіщо.** Supply chain починається з власного ноутбука: `curl | bash`
останньої версії — це довіра без перевірки. Однакові версії на всіх машинах
і в CI = відтворюваний результат.

**Питання.**
- Від чого захищає перевірка SHA-256, а від чого ні (підпис vs контрольна
  сума)?
- Чому `| head` під `set -o pipefail` може дати exit 141?

## Phase 4, крок 2 — Kyverno (`bbb1162` … `6e06dfd`)

**Що.** Kyverno 1.20, п'ять `ValidatingPolicy` (CEL): privileged, hostPath,
`latest`-тег, resource limits, runAsNonRoot. Режим вибирається міткою
namespace `lab/kyverno=audit|enforce`. Офлайн-тести `kyverno test` (85/85).
`make verify-admission` доводить, що Kyverno сам блокує под сценарію 1 у
namespace **без** PSA. Webhook fail-closed, інфраструктурні namespace
виключені (компенсується RBAC, див. `design-decisions.md`).

**Навіщо.** PSA покриває лише стандартні профілі; Kyverno додає власні
правила (теги образів, ліміти). Defense in depth: якщо хтось зніме PSA-мітку,
Kyverno все одно блокує. У 1.20 legacy `ClusterPolicy` вже не виконується,
тому одразу CEL-політики.

**Питання.**
- Fail-open чи fail-closed webhook: які ризики в кожного?
- Чому PolicyReport з'являється не одразу після деплою?
- Як довести, що спрацював саме Kyverno, а не PSA (порядок admission)?

## Phase 4, крок 3 — Falco (`18eece1`)

**Що.** Falco 0.45.2, драйвер `modern_ebpf`, без `privileged`: лише
CAP_BPF, CAP_PERFMON, CAP_SYS_RESOURCE, CAP_SYS_PTRACE. Автооновлення правил
(`falcoctl follow`) вимкнене.

**Навіщо.** Admission (PSA, Kyverno) бачить лише YAML у момент створення.
Що відбувається *всередині* контейнера потім (shell, читання токена,
мережеві з'єднання), бачить тільки runtime-сенсор. Сам сенсор — ціль для
атаки, тому мінімум привілеїв.

**Питання.**
- Чим admission control відрізняється від runtime detection і чому потрібні
  обидва?
- Чому modern eBPF кращий за kernel module у цьому кластері?
- Чому автооновлення правил детекції — ризик?

**Питання.**
- Як ти доводиш, що інфраструктура відтворювана, а не «працює на моїй
  машині»?
- Які кроки в цьому ланцюжку не ідемпотентні, і як `make` це обходить?
- Що в кластері *не* описано кодом (наприклад, стан БД) і чому це нормально
  для лабораторії?
